## 壹、 資安與資料治理類（Data Governance & Security）

### Q1：把銀行的 SQL 腳本交給 Copilot 分析，難道沒有原始碼洩漏或資安合規的風險嗎？

-   **評審關切點**：關注金融業對資料防護（Data Leakage）與原始碼保護的極高標準。
-   **風控話術核心**：**「原始 SQL 不離本機 + 純瀏覽器端靜態分析 + 非機敏摘要雙重人工人為把關」**

**【擬答】** 「非常感謝評審切中金融資安的核心！我們非常重視這個問題，因此本專案採用 **『零機敏外流』的人機雙重防線架構**：

1.  **原始 SQL 永遠留在本機**：SQL Compare 與靜態血緣分析 **100% 在使用者本機瀏覽器端執行**，原始 SQL 腳本、預存程序及生產資料庫連線字串**絕不上傳雲端**。
2.  **僅交接最小化結構摘要**：送到 Copilot Chat 的是一份不含原始 SQL 邏輯與運算式的 `schemaVersion 1.0` JSON 摘要，僅包含抽象化的變更與欄位關聯。
3.  **雙重人工確認防線**：在下載並提交 JSON 前，工具會提供預覽視窗，由風控人員親自確認裡面完全沒有真實客戶帳號、身分證字號或機敏資訊後才手動上傳。即使是測試租用戶，我們也嚴格遵守此一標準，徹底阻斷資安風險。」

* * *

### Q2：即使去除了原始 SQL，JSON 裡的資料表或欄位名稱如果包含銀行內部的商業機密怎麼辦？

-   **評審關切點**：考察物件命名（Metadata/Schema）是否有洩漏商業邏輯的疑慮。
-   **風控話術核心**：**「合成遮罩驗證 + 人工審查機制 + 備援本機流程」**

**【擬答】** 「這正是我們堅持『人工在迴圈中（Human-in-the-loop）』的原因！

1.  **展示與測試採用合成遮罩**：目前展示與測試均使用遮罩後的合成名稱（如 `DEMO_CUSTOMER`、`DEMO_RISK_SEGMENTATION`），不上傳任何真實銀行物件名稱。
2.  **上傳前的最終檢查權**：匯出 JSON 時，摘要預覽視窗會明確提醒操作者檢視物件名稱。若特定資料表名稱屬於核心商業機密，覆核者可選擇不手動交接，直接在本機工具端完成全人工覆核。
3.  **保留本機備援**：本原型即使完全不安裝或不使用 Copilot，本機 HTML/JSON 分析結果依然可單獨運作，確保在最高等級資安管制下業務完全不中斷。」

* * *

## 貳、 AI 幻覺與風險控制類（AI Hallucination & Accuracy）

### Q3：生成式 AI 經常產生「幻覺」（Hallucination），萬一 Copilot 漏掉重要的下游風險報表影響，或者憑空捏造不存在的欄位怎麼辦？

-   **評審關切點**：懷疑 AI 輸出的正確性，擔憂遺漏風控影響導致錯誤決策。
-   **風控話術核心**：**「證據鏈先行 + 固定提示限制 + 人工核對與最終簽核」**

**【擬答】** 「這正是我們不讓 Copilot 直接『讀 SQL 寫答案』的原因，也是本提案最大的創新點——**『證據鏈先行』的負責任 AI 協作**：

1.  **靜態分析提供客觀證據**：所有的欄位血緣與影響路徑（如 `SEGMENT_LABEL` 與 `RISK_BUCKET`）都是本機工具透過嚴謹語法樹解析產出的『客觀事實』，Copilot 絕無權限自行發明不存在的關聯。
2.  **固定提示詞（Prompt v1.1）嚴格限縮**：我們輸入給 Copilot 的指令明確限制：『必須嚴格依據 JSON `impacts` 節點進行摘要，禁止任何未經授權的推論』。
3.  **Copilot 僅做轉譯，風控保留最終判斷**：Copilot 產出的繁體中文清單僅做為整理待辦，覆核者會拿著這份待辦對照本機工具顯示的真實路徑進行人工簽核。Copilot 不會代為核准，更不會觸發系統部署，確保風控防線毫無漏洞。」

* * *

### Q4：如果 SQL 寫法太複雜（例如包含動態 SQL、`PIVOT` 或外包預存程序），靜態分析工具解析不出來怎麼辦？

-   **評審關切點**：測試工具對真實複雜環境與極端情境（Edge Cases）的防禦力。
-   **風控話術核心**：**「主動揭露不確定性 + 空結果不等於無風險 + 工程師人工補查」**

**【擬答】** 「我們作為風險管理人員，始終秉持\*\*『空結果不等於無風險』\*\*的嚴謹態度！

1.  **主動揭露解析限制**：在我們的 Demo 警告案例（`parser-warning.sql`）中，當語法遇到省略 `IN` 清單的複雜 `PIVOT` 時，工具摘要會主動帶出 `analysisMessages: [{level: "warn", count: 1}]` 警告。
2.  \*\* Copilot 提醒人工介入\*\*：Copilot Chat 收到這份摘要時，會依照固定提示語，在報告首頁以醒目字樣警示：『本清單因語法解析限制，不保證完整，請工程師回到本機工具檢視詳細訊息並人工補查未載入之程序』。
3.  **不遮掩限制，直面風險**：靜態分析一定有其邊界（如未載入的外部排程或動態 SQL），我們主動將限制轉化為風控檢核點，確保絕不盲目放行。」

## 參、 業務價值與效益量測類（Business Value & ROI）

### Q5：你們宣稱能提升覆核效率，但目前是否有真實環境測試或確切的省時數據？

-   **評審關切點**：質疑 ROI 試算是否為空中樓閣，評估數據的真實性。
-   **風控話術核心**：**「重實測、講口徑、不虛報 + 敏感度分析模型 + 真人配對實驗」**

**【擬答】** 「作為風控把關者，我們堅持\*\*『重實測、講口徑、不虛報』\*\*，絕不拿未經證實的推測數字來宣稱效益：

1.  **現階段僅完成技術回歸**：目前的 Colab full 自動化測試已實測通過 30 項基礎檢驗（包含 Node 契約與個資掃描），這證明了工具的技術穩定度，但我們明確標註『這不等於端到端人工節省工時』。
2.  **建立嚴謹的敏感度試算模型**：我們以銀行完全人力成本（NT$900/小時）為基準進行三種情境試算。在基準情境（年 300 件變更、每案節省 20 分鐘）下，每年可回收 **100 小時高價值工時（約 NT$90,000 價值）**。
3.  **未來的實測驗證承諾**：我們已擬定完整驗證計畫，下一步將進行至少 3 組真人配對（人工 vs 原型）計時與正確率量測，在取得確實統計數據前，我們保持嚴謹，絕不虛報未經證明的省時比例。」

### Q6：為什麼不直接把整個流程做成全自動 API 對接，反而保留「手動下載 JSON、再貼到 Copilot Chat」這種看似多餘的人工步驟？

-   **評審關切點**：挑戰系統架構的自動化程度與使用者體驗（UX）。
-   **風控話術核心**：**「輕量化極速落地 + 低損益兩平門檻 + 人工控制點 (Control Point)」**

**【擬答】** 「這正是我們從**業務落地可行性與合規風險**出發的精心設計：

1.  **實現『零額外 IT 採購成本』極速落地**：如果做成全自動 API 直連，銀行需要採購 Copilot Studio API、架設中間層伺服器、申請複雜的防火牆穿透，建置成本與資安審查動輒耗時數月。使用既有瀏覽器加上同款 M365 Copilot Chat 授權，初期建置成本為零，損益兩平門檻極低。
2.  **將手動轉譯做為『資安與責任斷點』**：在金融合規中，這一步『手動匯出與檢視』不是多餘的動作，而是關鍵的『控制點（Control Point）』。它確保了每一筆送出本機的資料都經過具體權責人員的審視，同時也明確落實了『覆核者保留最終核准權』的精神。」

## 肆、 系統技術與未來演進類（Architecture & Scalability）

### Q7：未來如果這套原型要在全行推廣，技術架構要如何延伸或對接企業級 CI/CD 流程？

-   **評審關切點**：評估專案從黑客松 Prototype 邁向 Enterprise Production 的擴充性（Scalability）。
-   **風控話術核心**：**「標準化 JSON 契約（Schema Versioning） + 模組化升級」**

**【擬答】** 「我們的系統設計具備高度的模組化與可擴充性：

1.  **契約與介面已標準化**：前端分析輸出的 JSON 採用了版本控制（`schemaVersion 1.0`），明確劃分了 `changeContext`、`impacts` 與 `analysisMessages` 結構。
2.  **靈活對接未來架構**：未來若銀行資安政策開放 Enterprise API 環境，底層的本機靜態分析引擎可以直接封裝為 CLI 或 Git 插件，在 CI/CD Pipeline 中自動執行，並將 JSON 送入企業級私有 LLM 進行自動化報告草擬，而前端的人工簽核流程與固定提示機制可完美無縫遷移。」
