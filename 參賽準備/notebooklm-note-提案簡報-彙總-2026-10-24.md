# SQL SPA Tools —— 用 M365 Copilot 支援風險管理 SQL 變更覆核提案報告

**提案單位**：鎖頭銀行（Lock Bank）風險管理部\[1\] **提案者**：Dunk（風險指標與報表變更覆核把關者）\[2\] **競賽專案期間**：2026 年 10 月 22 日 至 12 月 24 日\[2\]\[3\] **提案核心主張**：**「讓 Copilot 整理分析證據，讓風險管理覆核者保留最終判斷」**\[2\]

* * *

## 壹、提案背景與業務痛點分析

### 一、 提案者角色設定與業務視角 (Persona)

在鎖頭銀行的風險管理體系中，提案者 **Dunk** 的角色定位為 **風險指標與風險報表變更的「覆核把關者」**，而非底層系統開發人員\[3\]\[4\]。業務範疇專注於確保銀行風險指標、客戶信用分級與管理報表數據的準確性與一致性\[3\]\[4\]。

### 二、 核心業務痛點 (Pain Points)

1.  **變更影響鏈條長，跨腳本肉眼追查困難**： 當資訊或資料團隊異動上游 SQL 欄位定義時，風險覆核者必須跨多份 SQL 腳本追查下游 **「風險分群」（如信用風險等級、客群分級）** 與 **「管理報表」** 是否會產生計算失真或邏輯斷鏈\[3\]。
2.  **缺乏統一證據格式，溝通與稽核成本高**： 過去缺乏自動化且可追溯的分析工具，審查過程中全靠人工穿梭不同腳本比對，缺乏結構化的證據表達方式，導致風控與 IT 團隊對齊溝通耗時，且極易遺漏潛在風險\[3\]。

* * *

## 貳、核心業務主張與三大創新發想亮點

### 一、 核心提案主張

本專案提出 **「讓 Copilot 整理分析證據，讓風險管理覆核者保留最終判斷」** 的人機協作模式\[2\]。透過前端工具客觀釐清 SQL 欄位血緣，再由 M365 Copilot 將非機敏摘要轉化為易讀的覆核待辦，最終核准權仍嚴格歸屬於具權責的風控人員\[3\]\[4\]。

### 二、 三大業務創新發想亮點 (Business Innovations)

| 創新維度 | 傳統做法 / 通用 AI 痛點 | 本提案之業務創新亮點 |
| --- | --- | --- |
| 1. 協作模式 | 生成式 AI 容易產生幻覺、虛構不存在的資料表或關聯路徑[5][6]。 | 「證據鏈先行」的負責任 AI 協作：堅持「先有客觀分析證據，再由 Copilot 轉譯」，所有影響主張均須具備具體的原始欄位關聯路徑，嚴禁虛構相依性[3]。 |
| 2. 資安架構 | 直連生產資料庫或直接上傳原始 SQL，面臨極高資安與合規風險[5][6]。 | 「零機敏外流」的人機雙重防線：採用純瀏覽器端本機分析＋非機敏摘要人工交接；原始 SQL 與生產資料不離開本機，經覆核者雙重確認無個資後才手動交接[3]。 |
| 3. 風控思維 | 系統常忽略解析限制，空結果易被誤解為「無影響」而盲目放行[5][6]。 | 「主動揭露不確定性」的風控防線：遇語法解析限制時主動標註警告，Copilot 明確提醒「清單不保證完整，請工程師補查」。貫徹「空結果不等於無風險」的精神[3]。 |

## 參、業務操作與人機協作 5 大流程

本提案劃分出明確的人機分工界線，確保 AI 僅扮演輔助整理的角色\[3\]\[4\]：

```
[1. 掌握變更] ──> [2. 穿透影響] ──> [3. 安全確認] ──> [4. 智能轉譯] ──> [5. 最終覆核]
 (本機 SQL 比對)    (欄位血緣分析)    (雙重人為把關)    (Copilot Chat)   (人工簽核放行)
```

| 覆核階段 | 業務實際操作與體驗 | 人機責任界線與資安控制 |
| --- | --- | --- |
| 1. 掌握變更 | 開啟本機 SQL Compare 檢視欄位前後定義差異（如：客戶分群欄位長度擴增）[3]。 | 工具提供改動線索，由覆核者判讀其業務意義[4][9]。 |
| 2. 穿透影響 | 一鍵產出直接與間接影響路徑，直指「風險分群」與「管理報表」下游欄位[3]。 | 靜態分析限已載入腳本，未涵蓋之外部程序仍需人工補查[3]。 |
| 3. 安全確認 | 檢查非機敏摘要預覽（schemaVersion 1.0 JSON），確認無真實帳號或個資後匯出[3]。 | 雙重人工作業防線：由覆核者把關，原始 SQL 永不上雲[3]。 |
| 4. 智能轉譯 | 將結構化 JSON 上傳至 M365 Copilot Chat，套用固定提示（Prompt v1.1）轉為繁體中文影響說明與檢核清單[3]。 | Copilot 僅依證據彙整待辦，不代表核准、不觸發上線[3]。 |
| 5. 最終覆核 | 覆核者拿著 Copilot 條列的具體證據與限制，與 IT 團隊對齊並完成人工簽核[3]。 | 覆核者保留最終業務判斷與核准權[3]。 |

## 肆、展示案例與測試基準 (UAT Fixtures)

展示一律採用經遮罩之合成 SQL 與合成物件名稱，不使用任何真實客戶資料或銀行生產資料\[17\]：

### 一、 標準合成變更案例 (Normal Fixture)

-   **變更來源**：`DEMO_CUSTOMER.CUSTOMER_SEGMENT` 定義由 `VARCHAR2(20)` 改為 `VARCHAR2(40)`\[7\]。
-   **預期下游影響集合 (expected.json)**：
    1.  **間接影響（風險分群）**：`DEMO_RISK_SEGMENTATION.RISK_BUCKET`\[7\]
    2.  **直接影響（管理報表）**：`DEMO_MONTHLY_REPORT.SEGMENT_LABEL`\[7\]

### 二、 解析警告案例 (Warning Fixture: `parser-warning.sql`)

-   **測試情境**：語法中故意省略 `PIVOT` 之 `IN` 清單，摘要帶出 `analysisMessages: [{level: "warn", count: 1}]`\[22\]。
-   **驗證重點**：驗證 Copilot Chat 是否會主動指出警告訊息與靜態分析限制，並明確要求工程師回到本機工具檢視詳細訊息，不將目前清單誤標為完整\[14\]。

## 伍、成本效益與財務風控分析

本提案以金融風控人員 **「重實測、講口徑、不虛報」** 的嚴謹態度，進行財務與效益估算\[5\]。

### 一、 量化效益：工時容量回收敏感度分析

以銀行完全人力成本每小時 **NT$900** 為基準，針對每年覆核案件量進行三種敏感度情境試算\[5\]：

年回收工時\=年案件量×60每案節省分鐘​

年工時價值\=年回收工時×NT$900

| 敏感度情境 | 年案件量 | 每案節省時間假設 | 年回收工時 | 年工時價值 (NT$) | 業務效益說明 |
| --- | --- | --- | --- | --- | --- |
| 保守情境 | 120 件 | 10 分鐘 | 20 小時 | NT$ 18,000 | 釋放基礎審查能量[5] |
| 基準情境 | 300 件 | 20 分鐘 | 100 小時 | NT$ 90,000 | 顯著減少跨團隊來回溝通[5] |
| 高量情境 | 600 件 | 30 分鐘 | 300 小時 | NT$ 270,000 | 創造高價值重配置人力[5] |

### 二、 財務模型與損益兩平 (Break-Even) 估算

1.  **淨效益模型方程式**：

淨效益\=年工時價值−年化維護與授權總成本\[6\]\[26\]

1.  **損益兩平案件量方程式**：

損益兩平案件量\=時薪 $900×(每案節省分鐘÷60)年化總成本​\[6\]\[26\]

1.  **低門檻導入優勢**： 本原型採用既有純前端工具搭配既有 M365 Copilot Chat 授權，前期無需額外採購 Copilot Studio API、連接器或外部伺服器資源，因此損益兩平門檻極低\[6\]。

### 三、 質化效益與數據紀律護欄

-   **跨部門對齊零時差**：統一的覆核檢核清單與可回查證據路徑，大幅降低風控與 IT 團隊反覆核對的隱形成本\[6\]。
-   **數據紀律承諾**：上述試算為目標情境，非已實現成果\[6\]。本專案堅持規劃至少 **3 組真人配對計時與評分演練**，在取得確切實測數據前，絕不宣稱未經證明的省時比例\[6\]。

## 陸、技術驗證現況與資安防線

### 一、 Colab 自動化技術回歸紀錄 (2026-10-23)

-   **自動化測試數據**：Colab full 模式執行通過 **30 項實際檢查**（包含 10 項 Node 契約測試、12 頁瀏覽器載入、4 項主要功能操作、4 項個資檢查）\[31\]。
-   **合成測試案例**：另產生 1,000 筆固定種子案例，狀態標註為 `prepared`，嚴格註明**尚未逐筆執行，不計入通過數**\[31\]。
-   **效能微基準**：Oracle SQL Formatter 函式微基準 P50 於 100 / 1,000 / 10,000 筆分別為 13.3 / 94.8 / 501.6 ms（僅反映格式化函式吞吐量，不代表端到端人工節省工時）\[17\]。

### 二、 資安與資料治理防線 (Data Security Guardrails)

1.  **零機敏資料上傳**：嚴禁上傳帳號、身分證字號、金融識別資訊、密碼或連線字串\[16\]。
2.  **原始 SQL 不離本機**：送入 Copilot 的資料僅為最小化 `schemaVersion 1.0` JSON 結構化摘要，不包含原始 SQL 內容或運算式\[11\]。
3.  **無權限越界**：Copilot 不連接銀行生產資料庫、不執行 SQL 查詢、不修改腳本，亦不代替人員批准變更\[15\]。

## 柒、主要風險、因應對策與推廣時程

### 一、 主要風險與因應對策表

| 潛在風險 / 限制 | 提案因應對策 |
| --- | --- |
| 靜態解析未覆蓋動態 SQL 或外部報表[39][40] | 摘要攜帶限制與警告；空結果不解讀為無影響，由工程師人工補查[39][40]。 |
| Copilot 可能產生誤讀或虛構相依性[39][40] | 固定提示限制僅引用 JSON impacts；人工逐項核對證據，記錄錯誤回覆[39][40]。 |
| 物件名稱本身可能包含內部敏感資訊[39][40] | 展示使用合成名稱；下載前由操作者雙重檢查物件名稱是否可上傳[11]。 |
| M365 檔案上傳或讀取失敗[39][40] | 保留本機分析結果與 HTML/JSON 匯出檔，備妥人工流程備援[39][40]。 |

### 二、 推廣時程與四大階段規劃 (2026.10.22 — 12.24)

```
[階段一：凍結 MVP] ──> [階段二：配對量測] ──> [階段三：補強證據] ──> [階段四：展示排練]
 (10/22 — 11/05)      (11/06 — 11/30)      (12/01 — 12/14)      (12/15 — 12/24)
```

1.  **10/22–11/05 (凍結 MVP 階段)**：凍結 MVP 流程、合成案例 (`expected.json`)、預期答案與 Copilot 固定提示 (Prompt v1.1)\[41\]\[42\]。
2.  **11/06–11/30 (配對量測階段)**：執行至少 3 組人工與原型流程真人配對計時與步驟量測，演練正常與警告案例\[41\]\[42\]。
3.  **12/01–12/14 (補強證據階段)**：核對影響清單與 Copilot 回應證據一致性，回填實測數據至提案報告\[41\]\[42\]。
4.  **12/15–12/24 (展示排練階段)**：完成 Demo 講稿排練與故障備案準備，依官方規定完成最終作品提交\[41\]\[42\]。
