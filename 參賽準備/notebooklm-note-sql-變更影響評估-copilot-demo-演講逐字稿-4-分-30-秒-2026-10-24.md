# 🎙️ SQL 變更影響評估 Copilot Demo 演講逐字稿（4 分 30 秒）

**演示主題**：SQL SPA Tools —— 用 M365 Copilot 支援風險 SQL 變更覆核\[2\]\[8\] **演講者角色**：鎖頭銀行風險管理部 Dunk（風險指標與報表覆核把關者）\[2\] **總時長**：約 4 分 30 秒\[1\]

* * *

### 📋 Demo 前準備 checklist（演練防線）

1.  **測試數據準備**：載入測試資料夾內的合成 SQL 與預期結果檔（`customer-before.sql`、`customer-after.sql`、`downstream.sql` 及預期結果 `expected.json`）\[6\]\[9\]。
2.  **工具頁面開啟**：於瀏覽器開啟 SQL Compare 及 SQL 欄位血緣分析器，並準備解析警告案例 `parser-warning.sql`\[6\]。
3.  **M365 Copilot 設定**：準備清空的 Copilot Chat 對話視窗與 Prompt v1.1 固定提示\[6\]\[10\]。
4.  **測試數據邊界說明**：準備 Colab 回歸數據（30 項實測通過、1,000 筆為預備案例），絕不使用真實銀行 SQL、客戶資料或內部物件名稱\[6\]\[11\]。

* * *

### ⏱️ 逐段演講逐字稿與演練步驟

0:00–0:25｜一、問題與參賽目的（痛點揭示）

**「評審好，我是鎖頭銀行風險管理部的 Dunk。在銀行資料流程中，SQL 欄位一旦改動，工程師與風控覆核者必須跨多份腳本追查哪些風險指標和下游報表可能失真，並把依據及測試項目整理出來**\[4\]**。過去全靠人工肉眼穿梭比對，容易遺漏且對齊成本極高**\[5\]**。我們的原型採用 SQL SPA Tools 在本機完成靜態差異與欄位血緣分析，再讓 M365 Copilot Chat 協助轉譯為結構化待辦；而最終的風控核准權，依然由工程師與覆核者嚴格把關**\[4\]**。」**

* * *

0:25–0:55｜二、資料流程與資安護欄（零機敏外流雙重防線）

**「為了符合銀行嚴格的資安規範，原始 SQL 永遠留在使用者本機瀏覽器分析，絕不下傳或上雲**\[12\]**。系統工具會先產生不含原始 SQL 程式碼的非機敏摘要預覽，操作者經雙重人工檢查無個資後，才確認下載 JSON 手動送交 Copilot Chat**\[5\]**。Copilot 不會直連生產資料庫，也不會執行 SQL、批准變更或觸發部署**\[12\]\[13\]**。上傳前若對內容或資料分類有疑慮，流程便立即停止交接**\[12\]\[15\]**。」**

* * *

0:55–1:50｜三、正常案例實機操作（靜態血緣與穿透影響）

**「現在大家看到的是合成欄位 DEMO\_CUSTOMER.CUSTOMER\_SEGMENT，定義從 VARCHAR2(20) 擴增為 VARCHAR2(40)**\[16\]**。在 SQL Compare 中，結構摘要清晰定位出一項欄位定義異動**\[16\]**。當我們載入下游 SQL 腳本進行血緣分析，對照表呈現四筆關聯，其中兩筆屬於未變更的 CUSTOMER\_ID**\[16\]**。系統精準篩選出兩項受影響的下游欄位：直接影響的是管理報表 DEMO\_MONTHLY\_REPORT.SEGMENT\_LABEL，間接影響的則是風險分群 DEMO\_RISK\_SEGMENTATION.RISK\_BUCKET**\[16\]\[17\]**。」**

* * *

1:50–2:30｜四、摘要確認與 Copilot Chat 智能轉譯（證據鏈先行）

**「接著我們開啟 Copilot 摘要預覽視窗，輸入經人工核對的變更背景**\[16\]**。系統 JSON 會將該項資訊明確標記為『操作者輸入、工具未驗證』，避免 AI 與靜態分析證據混淆**\[16\]**。導出的摘要已徹底移除原始 SQL、運算式與路徑**\[16\]\[20\]**。將 JSON 手動交給 Copilot Chat 套用固定提示後，Copilot 隨即產出繁體中文影響評估與檢核清單，每項影響均附帶具體的原始關聯證據**\[10\]**。所有輸出均標示為建議事項，絕不宣稱自動核准**\[10\]**。」**

* * *

2:30–3:05｜五、解析警告情境展示（主動揭露不確定性）

**「風控的本質在於防範未然，因此我們特別測試了解析警告案例 parser-warning.sql —— 該語法故意省略了 PIVOT 的 IN 清單**\[6\]**。工具摘要會主動帶出一筆警告訊息 warn: 1**\[11\]\[22\]**。當貼入 Copilot Chat 時，Copilot 依照固定提示規則，明確提醒『目前清單不保證完整，請工程師回到本機工具檢視詳細解析訊息』**\[10\]\[11\]**。我們貫徹『空結果不等於無風險』的精神，絕不盲目放行**\[11\]\[14\]**。」**

* * *

3:05–3:30｜六、Colab 技術回歸證據（客觀研發數據）

**「在技術可靠性上，我們的 Colab full 自動化測試實際通過了 30 項基礎檢查，包含 Node 契約測試、12 頁瀏覽器載入、主要功能操作與 4 項個資掃描檢查**\[11\]\[23\]**。另外預先產生的 1,000 筆合成案例標註為準備中（prepared），尚未逐筆執行，我們絕不虛報通過數**\[11\]\[23\]**。這是工具層的本機技術回歸證據，不代替 Copilot 的回答品質或銀行租用戶驗收**\[11\]\[24\]**。」**

* * *

3:30–4:00｜七、效益驗證與數據紀律（嚴謹風控態度）

**「作為風險管理人員，我們堅持『重實測、講口徑、不虛報』**\[14\]\[25\]**。我們不預先承諾未經證明的省時百分比**\[26\]\[27\]**。驗證計畫已設計標準流程，將由相同案例比較傳統人工與原型流程，至少進行三組真人配對計時與步驟評分，精準記錄完成時間、影響命中率、漏列/誤列數以及 Copilot 證據支持率**\[9\]**。在實測數據回填前，我們不發表未經證實的成效結論**\[26\]\[29\]**。」**

* * *

4:00–4:30｜八、下一步規劃與結尾（核心主張再現）

**「總結來說，我們目前已完成本機摘要預覽、合成正常案例、預期影響集合與解析警告揭露機制**\[20\]\[26\]**。下一步將在銀行正式核准的 M365 租用戶環境中完成端到端演練與三組以上的配對量測**\[26\]**。我們再次強調提案核心主張：『讓 Copilot 整理分析證據，讓風險管理覆核者保留最終判斷』**\[3\]**！謝謝各位評審**\[25\]**！」**
